# StudySIM1c-scoped — the StudyB-baselines arms in a world with no host-offload tier

**CPU only on the flash host. No GPU, no model server, no inference.** Every latency comes from the StudySIM1 engine model, every score from StudyD14b's committed traces and every recall answer's correctness from StudyB-baselines' committed per-question tables. No result marked INVALID is used.

**This report tabulates. It makes no claim about which baseline is best beyond the tables, and our scheduler is not in this study.**

---

## 0. THE SCOPE — read this before any number

* **The world.** one 32B vLLM 0.31.0 replica with NO host-offload tier: GPU-warm, cold and device fallback only
* **What is excluded.** the HOST-WARM readiness state and the OFFLOAD_TO_HOST action
* **Why.** StudySIM1's calibration gate failed only in KV-HOST cells, and StudySIM1b's mode-cost model leaves it at 69 % against an 80 % bar. The simulator does calibrate where there is no host-offload tier, and this study runs only there.
* **What this cannot claim.** nothing here bears on any arm's behaviour WITH host offload, and nothing here says which baseline is best beyond the tables

The exclusion is enforced by an **availability flag in the harness** (`run.py`: `HOST_AVAILABLE = False`, which maps OFFLOAD_TO_HOST to EVICT and never reports readiness HOST-WARM). **No baseline's logic was edited.** An arm whose core decision IS host offload is not run at all.

## 2. Which arms run, and which do not

40 arms in the suite: **37 runnable in scope** (of which 2 are oracles, reported separately as upper bounds) and **3 NOT RUNNABLE**.

| arm | why it is not runnable in this scope |
|---|---|
| `attentionstore` | AttentionStore IS a host-side KV cache hierarchy: its contribution is keeping whole attention caches on host memory and the scheduling that depends on them. With no host tier the paper's object does not exist, and what would run is not AttentionStore. |
| `lmcache` | LMCache IS a CPU/disk KV cache layer under the engine. With no host tier it reduces to the engine's own GPU prefix cache, which is what `always-cloud-fcfs` already is. |
| `pensieve` | Pensieve's mechanism is MULTI-TIER PARTIAL RESIDENCY, adapted here (adaptation A1) as whole-session OFFLOAD_TO_HOST because our action space has no partial tier. Removing the host tier removes the mechanism itself, not a component of it. |

| arm | host offload is one component; what the flag changes |
|---|---|
| `ekya` | decides episodic resource allocation; it demotes every session unconditionally |
| `clockwork` | decides admission from a predicted LOAD time; the COLD branch of that prediction is used instead of the HOST-WARM branch |
| `preble` | decides request order by prefix affinity; its AFFINITY weight for HOST-WARM (0.5) never applies |
| `mooncake` | decides request ORDER by prefix affinity; readiness HOST-WARM simply never occurs |
| `kvflow` | decides WHICH sessions stay GPU-warm (workflow-aware eviction); the demotion target is not the decision |
| `covstream` | keeps its top-4 coverage sessions GPU-warm and demotes the rest |
| `B9-best-of-breed` (run as **B9-noHost**) | uses host offload as ONE component among several; runs as the labelled variant B9-noHost with that component disabled and every other component and the precedence order unchanged |

`B9-best-of-breed` runs as the labelled variant **B9-noHost**: its host-offload component is disabled by the harness flag and every other component, and the precedence order, are unchanged.

## 8. What this cannot claim

* **Nothing about host offload.** The HOST-WARM tier does not exist in this world. Three arms whose contribution IS that tier were not run, and every other arm's demotions land in EVICT rather than on the host. A reader who wants the host-offload comparison needs StudySIM1b's gate to pass first; it does not.
* **No ranking beyond the tables.** The tables are what was measured. No arm is called better than another here, and our scheduler is not in this study, so nothing here is evidence for or against it.
* **N = 3 over-queueing.** The model over-queues at N = 3 by 1.21-1.27x in p99. Every N = 3 number carries that.
* **The device recall proxy.** A DEVICE recall answer is scored with StudyE7 Job A's committed flags, which are the H100 4B's. StudyD15 Part A rejected that as an EXACT device stand-in, so device recall numbers are valid for ORDERING and first-order value and are not exact device numbers.
* **Device recall latency is a rule, not a measurement.** StudyF4 measured device recall ACCURACY, not latency; the nearest committed device-side request latency (StudyD8 arm A total p50, 0.567 s) is used. It is far inside every deadline tested, so no result turns on it, but it is not a measurement of device recall.
* **The mix and ladder reading.** The specification's three mixes and its '2-32 episodic streams x 2-32 recall sessions' ladder are read as one ladder parameter and a mix that sets the ratio, because a full cross product would make the three mixes redundant with the ladder's own two axes. The alternative reading is a five-fold larger sweep.
* **JPEG is not validated.** Every episodic number here is PNG, StudyE9b setting (ii). StudyE10a-full did not establish JPEG accuracy parity for S-EMBER.
