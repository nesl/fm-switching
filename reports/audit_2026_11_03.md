**No device-versus-cloud comparison in the record is run on identical input.**

| comparison | model | host | stack / kernel | decoding | input |
|---|---|---|---|---|---|
| (a) K1 vs K3 | both 32B-I | both H100 | both vLLM | both greedy `t=0.0` | **differs** — window, frame count and resolution move together |
| (b) C2 vs C1 | both 4B | both flash | both llama.cpp F16 | both greedy | **differs** — window and frame count |
| (c) K1/K3 vs 4B-I | **32B vs 4B** | **H100 vs other** | **vLLM vs HF fa2** | greedy both | frames matched at the median |
| (d) ERQA C vs A_h100 | **32B vs 4B** | both H100 | both `sdpa` | both greedy | identical — but **both are cloud-hardware runs** |
| (e) MV-RoboBench C vs R4 | **32B vs 4B** | **H100 vs 3090 Ti** | both `sdpa` | both greedy | identical questions |

The only arms that run on an actual device tier — the Jetson Orin (StudyDevFast, StudyDevOne, StudyDeviceLatency) — have **no cloud counterpart on the same input**. StudyDevOne built `results/device/identical_input_manifest.json` (120 questions × N ∈ {37, 18, 9, 1}, per-PNG sha256) specifically so the H100 could replay byte-identical payloads, and **that replay has not happened**: StudyDevOne Part 3 records that the Orin cannot resolve the H100 host, so the comparison remains unmade. Every device-vs-cloud accuracy gap quoted anywhere in the record is therefore a comparison across at least model size and serving stack, and usually host as well.

**No cloud number includes a network.** All cloud serving in this repository is reached over loopback: `experiments/cost/study_x_vllm.py` sets `BASE = http://127.0.0.1:{PORT}` and `experiments/sember/study_r1_vllm.py` binds the server with `--host 127.0.0.1`. Every cloud TTFT, latency and p99 is therefore a same-host measurement with no link, no RTT and no bandwidth limit. The D2 uplink figures in §i are **payload sizes**, computed as `len(HTTP body)`, not transfer times — no number in the record converts them into a transfer cost over a real link.

### 2. E24c's INVALID reason was wrong; status unchanged

The main audit described all three E24 studies as comparing "deterministic single-point rules whose action spaces are disjoint singletons". **That is accurate for E24 and E24b and wrong for E24c.** Checked separately against each study's own code:

| study | code | what the policies actually are |
|---|---|---|
| E24 | `simulator/provisioning/sweep.py` | Seven deterministic single-point rules, no candidate set or allocator. `JointPolicy` = (predicted node, `CHEAPEST_SUFFICIENT[regime]`); `FidelityOnlyPolicy` = (**current** node, cheapest); `PlacementOnlyPolicy` = (predicted node, **always full**). Disjoint singletons — **confirmed**. |
| E24b | `simulator/provisioning/sweep_b.py` | Nine policies, same structure. `JointBPolicy` = (predicted node, `cheapest_sufficient_tau`); `FidelityOnlyBPolicy` = (`sess.serving_node`, `cheapest_sufficient_tau`). Both gained a shared cloud-fallback branch, which does not change the single-point structure. Disjoint singletons — **confirmed**. |
| E24c | `experiments/orchestration/sweep_e24c.py`, `simulator/provisioning/solver_c.py`, `policies/c/` | **NOT single-point rules.** All ten policies share one value function and one greedy allocator; `solver_c.py` states they "differ only in which (session, node, fidelity) candidates they pass to the allocator — not in how they score or pack them." `JointC` passes the full node × fidelity product space; `FidelityFirst` passes that space filtered to `cheapest_sufficient_tau`. **Joint's action space strictly CONTAINS the decomposed policies'** — the opposite of the E24/E24b defect. |

**E24c's actual defect is a misspecified value function.** `V(i, j, f) = P_serve × 1[sufficient(f, regime, tau)] × latency_saved_s` with `latency_saved_s = cold_prefill(full, L, node_tier)`: V does **not** depend on `f` beyond the binary sufficiency test, so all sufficient fidelities carry identical value while `_s_ready_gb` differs by orders of magnitude:

| fidelity | S_ready | density vs `win` |
|---|---|---|
| `sum80` | 4.59 MB | **25.6× denser** |
| `sum200` | 11.47 MB | 10.2× denser |
| `win` | 117.44 MB | 1× |
| `full` (L = 20,092) | 1.15 GB | sum80 is **251× denser** |

`greedy_knapsack` ranks by density = value / s_ready_gb, so the larger candidate set *steers* joint into the smallest sufficient representation, and refresh/maintenance cost appears nowhere in V. A greedy over a superset can underperform a greedy over a filtered subset when the ranking metric is misspecified, which is what happened. The reported median gap (joint − best-decomposed = −1.3 pp) measures an **incomplete objective**, not the absence of coupling value — the same conclusion E24c's own root-cause note reaches. **INVALID status unchanged for all three; only E24c's stated reason is corrected.**
