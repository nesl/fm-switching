# Scheduling policy: design decisions and pinned items

Living log for the scheduler design discussion (started 2026-11-15). Decisions are what we have agreed; hypotheses are expectations to test, NOT design constraints; pinned items are deliberately deferred and must be revisited. The current specification is v4 = `claude/policy_spec_v4.md` (D59), which supersedes v3 (`claude/policy_spec.md`) and the v3.1 addendum (`claude/policy_spec_v3_1_addendum.md`). Later rows revise earlier ones where noted.

## Problem-setting rules (standing; apply to every design, prompt and evaluation)

- MEMORY CAPACITIES ARE INPUTS, NOT CONSTANTS (D56). GPU KV pool and host tier sizes are parameters of the problem. The H100's large host memory is platform specific and must never be treated as a rule or used to argue that a decision is trivial.
- EVIDENCE THAT REACHES THE CLOUD IS NEVER DISCARDED (D56). Every device history lives in one of three tiers: GPU-warm, host-warm, or COLD (raw frames on disk, rebuilt by prefill when needed). "Dropped" means demoted to cold, never deleted.
- WHERE TO STORE EACH HISTORY (GPU / host / cold) IS A CORE DECISION under whatever capacities apply (D56).
- DEVICES NEVER SHARE CACHE ENTRIES in any evaluation (D84): per-device cache salt and per-(device, frame) multimodal UUIDs.
